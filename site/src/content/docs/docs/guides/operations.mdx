Each frame operation returns a new frame, and the schema of that new frame depends on the operation and on its arguments. The checker works out that schema with the typing rules of Polars, from the schema of the input frame and the arguments of the call. If Polars refuses the call, for example because it reads a column that the frame does not have, the checker reports an error.

Some operations do not change the columns at all, such as `sort`, `head`, `unique` or `filter`. Their result keeps the schema of the input.

## Choose and name columns

`select`, `with_columns`, `drop` and `rename` decide which columns the result has, and what their names are. In the example below, `drop` removes `quantity`, and `rename` turns `price` into `px`:

<Example name="ops_columns" />

Reading a column that the frame does not have is an error. Producing two columns with the same name is an error too, because Polars refuses a frame with two columns of the same name.

## Join

A join keeps the columns of both frames. When a column of the right frame has the same name as a column of the left frame, and it is not a join key, Polars adds the suffix `_right` to it, and the checker does the same. Here both frames have `price`, so the result has `price` from `trades` and `price_right` from `quotes`:

<Example name="ops_join" />

The join keys of the two frames need data types that Polars can match. A `String` key against an `Int64` key, for example, is an error. `join_asof` and `join_where` are checked in the same way.

## Group and aggregate

`group_by(...).agg(...)` returns the grouping keys, plus one column for each aggregation. Each aggregation keeps the name of the column that it reads. The shorthands, such as `len()`, `sum()` and `max()`, give their own columns:

<Example name="ops_group_by" />

`rolling(...).agg(...)` and `group_by_dynamic(...).agg(...)` group the rows into windows along an index column. The checker makes sure that the index column has a data type that the call accepts, such as a date or an integer.

## Reshape

`unpivot` turns columns into rows. Its result has the index columns, plus a `variable` column that holds the old column names and a `value` column that holds their values. `with_row_index` adds a column that numbers the rows:

`pivot` turns rows into columns. `explode` turns each element of a `List` or `Array` column into a row of its own, so it needs a column of one of those data types. `unnest` turns the fields of a `Struct` column into columns, so it needs a `Struct` column:

## Combine frames

`pl.concat` with `how="diagonal"` combines frames by column name: the result has every column of every frame. A column that appears in several frames has to have the same data type in each of them:

<Example name="ops_concat" />

A vertical concat stacks frames by the position of their columns, not by their names. A type does not track the order of the columns, so the checker cannot type the result, and it returns a plain frame. The setting `disallow_vertical_concat` turns every vertical concat into an error. `hstack`, `vstack`, `extend` and `merge_sorted` are checked too.

## Fill and reduce

`fill_null` and `fill_nan` can change the data type of a column, because Polars casts the column to fit the fill value. `fill_null(0.5)` on an `Int64` column, for example, gives a `Float64` column, and the checker gives the same data type.

The whole-frame reducers, such as `sum()` and `mean()`, reduce each column to one value, so they return a frame with one row. Each column gets the data type that the reducer gives it in Polars. `mean()` of an integer column, for example, is a `Float64`.
