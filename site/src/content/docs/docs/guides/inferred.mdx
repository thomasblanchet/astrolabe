Writing out the return type of a function is not always practical. The type of an expression is long, because it holds the code of the expression. And a function that changes an open frame returns the columns of its caller, which only the body determines. Such a function can let the checker work out its return type from its body. You write an inferred type as the return type, and you wrap each value that the function returns in `infer(...)`. At each call, the result is the union of the types of those values.

This is the intended way to type a function that changes an open frame. A remainder marker written by hand only repeats what the body does, and it has to change each time that the body changes.

| Return type | The function returns |
| -- | -- |
| `InferredExpr` | Expressions. |
| `InferredDataFrame` | Eager frames (`DataFrame`). |
| `InferredLazyFrame` | Lazy frames (`LazyFrame`). |
| `TypedDataFrame[Schema, InferredRemainder]` | A frame with the columns of `Schema`, plus a remainder that the checker works out. |

## Return the declared columns and an inferred remainder

Sometimes you want to declare the columns of the result, and let the checker work out only the remainder. `TypedDataFrame[Schema, InferredRemainder]` does that. The declared columns of the result are those of `WithNotional`, and the checker works out the remainder. At this call, the remainder is `symbol`:

Each returned value has to contain every column of the declared schema, with a data type that matches. The checker reports a value that does not, at its `infer(...)`.

## Rules of use

- Write `infer(...)` around the whole value of a `return` statement.
- Use an inferred type only as the return type of a function. Anywhere else, such as on a parameter, it is an error.
- A function with `InferredDataFrame` must return a `DataFrame`, and a function with `InferredExpr` must return expressions.

<Example name="inferred_misuse" />

If one returned value has a plain type, which the checker does not track, the whole return type falls back to that plain type. By default this happens without an error. The setting `disallow_implicit_inferred_fallback` makes it an error. See [Configuration](../../reference/configuration/).
