For each result, the checker reaches one of three outcomes:

- **Proved.** The result has a type, and the checker continues from it.
- **A mistake.** Polars refuses this code at run time, so the checker reports an error.
- **Unproven.** The checker cannot decide. The code can be correct, but nothing in the types shows it.

## Why a result can be unproven

A result is unproven for a reason, and the code can often remove that reason:

- A column name is a variable, not a literal string, so the checker cannot know which column the code reads.
- A Python function computes a column, and no `return_dtype=` states the data type that the function returns.
- A reader gets no schema, so the checker cannot know the columns of the frame.
- A remainder contains a name for some callers and not for others, so the result depends on the caller.

## What the checker does without a proof

When the checker cannot prove a result, it keeps as much of the type as it can:

- If it knows the name of a column but not its data type, the column gets the data type `Unchecked`, and the rest of the frame keeps its schema.
- If it knows nothing about the columns, the result is a plain frame, which the checker does not track.

## You choose what to accept

Each reason has a level. The levels range from reasons that a strict program can always avoid, to reasons that only a promise from the caller can remove. The setting `allow_unproven` sets the level that the checker accepts without an error. When the checker reports an unproven result, the note under the error names the level that accepts it, and the operation that it comes from.

A codebase can start at the default level, and raise the level as its code states more. See [Configuration](../../reference/configuration/).

## Checker gaps

A checker gap is a case that the plugin does not model. The cause is in the plugin, not in your code, so there is nothing in your code to fix. A gap passes at every level except `never`, and the setting `report_checker_gaps` lists all of them.
