A frame type is a claim about the schema of a frame. When the checker reports no error, at a level that accepts no unproven result, it proves this claim: as long as the frames that enter the program have their declared schemas, every operation finds each column that it reads, with a data type that it accepts.

The condition matters. The checker proves that the code agrees with the declared types. It does not prove that a file on disk agrees with them. So check each frame from outside the program once, where it enters the program, with `check_schema`. See [Runtime checks](../../guides/runtime/).

## What no type can see

A type holds the names and the data types of the columns, and nothing more. So no type can know:

- **The values.** Nulls, ranges, duplicates and the value of a literal belong to the data. A cast that fails for some values, such as an integer too large for the target data type, passes the checker.
- **The number of rows.** `df.select(pl.col("b"), pl.col("a").head(2))` puts two columns of different lengths side by side. Polars raises an error unless the two lengths happen to match, and a type does not know the lengths.
- **The order of the columns.** A vertical stack such as `vstack` matches the columns of two frames by position. The checker compares names and data types only, so Polars can still raise an error for two frames whose columns are in a different order.

## Limits of the design

Some limits are deliberate:

- A join that renames a column for some callers and not for others is an error, not a result. A promise on the remainder, `disjoint_from=`, removes the error.
- An expression that a newer release of Polars adds gives an `Unchecked` column, under the name of the expression.

## Behaviors of Polars

Some calls are valid according to the type stubs of Polars, but fail at run time. Some results depend on behavior of Polars that no rule captures. The checker works around every such case that it knows. See [Polars behaviors](../../spec/polars-behaviors/).
