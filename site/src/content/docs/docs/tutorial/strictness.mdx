The checker cannot always prove a result. Sometimes it knows the name of a column but not its data type, and sometimes it cannot know the columns of a frame at all. In each case, the checker does not guess. It records the reason, and one setting decides which of these unproven results are reported as errors.

## A result without a proof

`map_elements` runs a Python function on each value of a column. The checker cannot look inside that Python function, so it cannot know the data type of the result:

<Example name="tut_strict_default" />

The column `price` keeps its name, but its data type becomes `Unchecked`, which means that the data type is unknown. Everything else is still checked: the other columns keep their data types, and a later step can still read `price` by name.

## Make it an error

The setting `allow_unproven` takes a level. Each level accepts some unproven results, and a stricter level accepts fewer of them. At the level `stated`, the same line is an error:

```toml title="pyproject.toml"
[tool.astrolabe]
allow_unproven = "stated"
```

<Example name="tut_strict_stated" />

The note under the error names two ways to let the line pass: a less strict level for the whole project, or an override for this one operation.

## Give the checker the proof

Here, the better fix is to state the data type of the result. `return_dtype=` tells Polars, and the checker, which data type the Python function returns, so the column is typed again:

<Example name="tut_strict_fixed" />

The default level is `omitted`. A new project can start at a stricter level, and an existing codebase can start at the default and raise the level later. See [Configuration](../../reference/configuration/) for each level, and [Adopting in an existing codebase](../../guides/adopting/).
