Pipelines are usually split into functions. A function typically reads a few columns of the frame that it receives, while its callers pass frames with many more columns. To accept those frames, the function declares only the columns that it reads, and a remainder stands for the rest.

## Declare the columns that the function reads

A `Columns` class lists columns and their data types, much like a dataclass lists fields. `other_columns()` declares a remainder: a name that stands for the columns of a frame that its type does not list. You pass the remainder as the second argument of `TypedDataFrame`:

<Example name="tut_functions_define" />

`TypedDataFrame[Priced, Rest]` accepts any frame that has `symbol`, `price` and `quantity`, whatever other columns the frame also has. A frame type with a remainder like this is an open frame. A frame type without a remainder, such as `TypedDataFrame[Turnover]`, is a closed frame: it has exactly the declared columns, and no others.

## Each call is checked

<Example name="tut_functions_call" />

- `blotter` has the three declared columns, plus `venue`. The remainder takes `venue`, so the call passes.
- `quotes` has no `quantity` column, so it does not fit the parameter type. The checker reports the mistake at the call, not inside the function.

## The body sees only the declared columns

Inside the function, the checker knows only the declared columns. Some callers pass a frame with `venue`, and others pass a frame without it, so the body cannot rely on `venue`:

<Example name="tut_functions_body" />

The checker cannot tell whether `Rest` contains `venue`, so it cannot give the result of `group_by("venue")` a schema, and it reports the line. The note under the error names the level of the setting `allow_unproven` at which this line is accepted. The chapter [Make the checker stricter](../strictness/) explains the setting.

If the function needs `venue`, declare it in the class of the parameter. The body can then use it, and every caller has to pass a frame that has it.
